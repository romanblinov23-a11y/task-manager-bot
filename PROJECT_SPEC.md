# Спецификация: Telegram-бот менеджер задач (рабочее название — "третий бот")

Это бот по аналогии с уже существующими у Романа ботами «Фёдор» (личный
ассистент) и «Иван» (аналитика Surf Coffee). Технический стек по аналогии:
Python + Railway + Anthropic API (claude-sonnet-4-6) + Google Sheets API
(аналог Notion PAT у предыдущих ботов) + Telegram Bot API.

Бот выполняет роль проджект-менеджера: фиксирует договорённости и задачи
из рабочих чатов, личных сообщений и протоколов встреч, опрашивает
сотрудников по статусам, ведёт три проектные таблицы в Google Sheets и
формирует отчётность — ежедневную, мгновенную (по событиям) и еженедельную
(аналитическую).

---

## 1. Проекты и структура данных

Три проекта, каждый — своя Google Таблица:

- **Парк Горького**
- **Окко**
- **Аврора**

К каждой таблице/проекту может вести один или несколько Telegram-чатов.
Сопоставление `chat_id → project` хранится в конфиге бота (не в таблице).
Смешанных чатов (один чат = несколько проектов) не существует — это
упрощает экстракцию задач, т.к. проект чата всегда известен заранее.

### 1.1. Категории задач (фиксированный список, не расширять без явного запроса)

1. Техническое обеспечение
2. Сервис
3. Команда
4. Маркетинг
5. Бухгалтерия
6. Административные
7. Ноу-Хао
8. Управленческая отчётность

### 1.2. Структура Google Sheets (одинаковая для каждого из 3 проектов)

Каждая таблица содержит три листа.

#### Лист 1 — "Задачи" (одна строка = одна задача, обновляется на месте)

| Колонка | Тип | Описание |
|---|---|---|
| `task_id` | текст | уникальный ID, формат `TASK-0001` |
| `created_at` | дата-время | когда задача зафиксирована |
| `source` | текст | `chat` / `manual` / `protocol` |
| `source_chat` | текст | название/ID чата, откуда пришла (если из группы) |
| `source_link` | текст | ссылка на исходное сообщение в Telegram |
| `project` | текст | Парк Горького / Окко / Аврора |
| `category` | текст | одна из 8 категорий (см. 1.1), строго из списка |
| `task_text` | текст | суть задачи |
| `assignee` | текст | имя сотрудника |
| `assignee_telegram_id` | число | для отправки личных сообщений |
| `deadline_original` | дата | первоначальный срок |
| `deadline_current` | дата | актуальный срок (после переносов) |
| `status` | текст | `новая` / `в работе` / `выполнена` / `просрочена` |
| `last_comment` | текст | денормализованная копия последнего комментария (источник правды — лист "Комментарии") |
| `needs_help` | да/нет | флаг "просил помощи Романа" |
| `last_status_check` | дата-время | когда бот последний раз спрашивал статус |
| `closed_at` | дата-время | когда задача закрыта (пусто, если открыта) |

#### Лист 2 — "Лог переносов и изменений" (append-only, никогда не редактировать старые строки)

| Колонка | Тип | Описание |
|---|---|---|
| `task_id` | текст | ссылка на задачу из листа 1 |
| `timestamp` | дата-время | когда произошло событие |
| `event_type` | текст | `перенос_срока` / `завершение` / `запрос_помощи` / `смена_статуса` |
| `old_value` | текст | что было |
| `new_value` | текст | что стало |
| `reason_comment` | текст | причина/комментарий сотрудника |

#### Лист 3 — "Комментарии" (append-only, полная история переписки по задаче)

| Колонка | Тип | Описание |
|---|---|---|
| `task_id` | текст | ссылка на задачу |
| `timestamp` | дата-время | когда оставлен |
| `author` | текст | `сотрудник` / `Роман` / `бот` |
| `comment_text` | текст | сам текст комментария |
| `related_status` | текст | статус на момент комментария (опционально) |

Уже готовые XLSX-файлы с этой структурой (заголовки + выпадающие списки)
лежат в `/mnt/user-data/outputs/` проекта — три файла, по одному на
проект. Их нужно вручную загрузить в Google Drive и открыть как Google
Таблицы (Drive сам предложит конвертацию), либо воссоздать структуру
напрямую через Google Sheets API при инициализации бота.

## 2. Входные каналы (три штуки, единая логика обработки на выходе)

### 2.1. Тег бота в рабочем групповом чате

- Бот состоит участником в рабочих чатах. Чат привязан к одному проекту
  через конфиг `chat_id → project`.
- Бот **постоянно тихо принимает** все сообщения в скользящий буфер
  (хранить последние ~2-3 часа), не анализируя их, пока не вызван.
- Триггер обработки: тег бота (`@botname`) или reply на сообщение бота.
- При триггере бот берёт буфер сообщений за последние ~2 часа
  (включающий момент тега) и отправляет его в Промпт 1 (экстракция).
- **Из одного контекста переписки может быть извлечено от 0 до N задач**
  — не ограничиваться задачей, ближайшей к тегу.

### 2.2. Личное сообщение Роману боту

- Любое сообщение Романа боту в личке может быть как разовой задачей,
  так и протоколом встречи — бот сам определяет это по содержанию
  (явного разделения командами не делать, это решает Claude в Промпте 1).
- Поскольку контекст чата здесь неоднозначен (не привязан к конкретному
  проекту автоматически), Claude должен определить проект:
  - по исполнителю, если он уже встречается в одной из трёх таблиц;
  - если неоднозначно — бот должен явно спросить Романа, к какому
    проекту относится задача, до того как показывать её на подтверждение.

### 2.3. Файл/текст протокола встречи

- Роман отправляет текстовый файл или вставляет текст протокола боту в
  личку (технически обрабатывается тем же путём, что 2.2 — бот сам
  определяет объём контента).
- Протокол может содержать задачи на людей из **разных** проектов
  одновременно — на выходе экстракция может дать несколько групп задач,
  каждая со своим целевым проектом/таблицей.

---

## 3. Логика подтверждения задач

После экстракции (Промпт 1) бот всегда показывает результат **Роману в
личку** перед записью в таблицу — никогда не пишет в таблицу автоматически
без подтверждения.

- Если задач несколько — показывать списком, с возможностью подтвердить
  все сразу или по одной.
- Если у задачи `assignee_unclear: true` или `confidence: "low"` —
  явно помечать в карточке (например, "⚠️ не уверен в исполнителе"), но
  **не отбрасывать автоматически** — показать Роману для решения.
- Варианты ответа Романа на карточку: Да / Править / Отмена.
- Только после "Да" задача записывается в Лист 1 нужной таблицы (плюс,
  если применимо, первая запись в Лист 3 "Комментарии" с автором "Роман"
  или "бот", фиксирующая создание задачи).

---

## 4. Цикл опроса статусов

- APScheduler проверяет таблицы на задачи с подошедшим/просроченным
  `deadline_current`.
- Бот пишет исполнителю **в личку** (не в общий чат) вопрос о статусе.
- **Технический нюанс Telegram API**: бот не может писать пользователю в
  личку, если тот никогда не инициировал диалог с ботом (`/start` или
  любое сообщение). При первом запуске нужен разовый онбординг — каждый
  сотрудник один раз пишет боту, чтобы открыть возможность личных
  сообщений. Сопоставление Telegram-аккаунта с именем в таблице бот
  делает сам, считывая username/имя профиля из группового чата.
- Ответ сотрудника обрабатывается Промптом 2.
- **Если статус неясен из ответа** (`status_clear: false`) — статус НЕ
  меняется автоматически. Бот сразу отправляет сотруднику уточняющий
  вопрос (`clarifying_question` из ответа Промпта 2) в той же переписке,
  и ждёт новый ответ — цикл повторяется до получения ясного статуса.
  Комментарий при этом всё равно сохраняется в Лист 3, даже если статус
  не прояснился.
- Когда статус определён — обновляется Лист 1 (`status`,
  `deadline_current` при переносе, `last_comment`, `needs_help`,
  `last_status_check`, `closed_at` при завершении), плюс добавляется
  запись в Лист 2 (если событие — перенос/завершение/смена статуса) и в
  Лист 3 (всегда, текст ответа сотрудника).

---

## 5. Мгновенные сигналы Роману

Бот немедленно (без батчинга, каждое отдельным сообщением) уведомляет
Романа в личку при одном из трёх событий, определённых Промптом 2
(`signal_type`):

1. **Завершение задачи**
2. **Запрос помощи** (`needs_help: true`)
3. **Перенос срока**

Приоритет при одновременном попадании нескольких признаков:
запрос_помощи > перенос_срока > завершение (см. инструкцию в Промпте 2).

---

## 6. Ежедневный отчёт

- Раз в день (вечером, точное время фиксируется в конфиге) бот отправляет
  Роману в личку текстовый отчёт по задачам с подошедшим сроком за
  сегодня: кто на месте, кто затягивает, где видна потребность в помощи.
- Источник данных — прямой подсчёт по Листу 1 (без обращения к Claude).

---

## 7. Еженедельная аналитика (пятница, 22:00)

- Полностью текстовое сообщение в личку Роману (без таблиц/файлов).
- Также доступно по запросу в любой момент (не только по расписанию).
- Структура отчёта — **с разбивкой по трём проектам**, не единым полем:
  1. Раздел по каждому проекту (Парк Горького / Окко / Аврора):
     - короткая сводка (закрыто / в работе / просрочено за неделю)
     - по каждому сотруднику проекта — 1-2 предложения наблюдения
       (НЕ оценка, НЕ балл эффективности — только сырые цифры + факт-ориентированный комментарий)
     - раздел "Задачи, требующие внимания" — что застряло именно в этом
       проекте (2+ переноса, давно нет обновления, срок близко без
       движения)
  2. Финальный раздел — сводка по сотрудникам, занятым в **нескольких**
     проектах одновременно: суммарная нагрузка, перекосы между
     проектами. Раздел пропускается целиком, если таких сотрудников нет.
- Цифры считает код (агрегация по Листам 1 и 2 каждой из трёх таблиц).
  Claude (Промпт 3) получает уже посчитанные агрегаты и формулирует
  наблюдения — НЕ считает сам и не присваивает оценок/баллов.

## 8. Промпты для Claude API

### 8.1. Промпт 1 — экстракция задач (общий для всех трёх каналов)

```
Ты — модуль анализа задач для бота-менеджера проектов Романа.
Твоя задача — найти в переданном тексте все рабочие договорённости
и задачи, которые нужно зафиксировать.

КОНТЕКСТ ВХОДНЫХ ДАННЫХ
Тебе передан один из трёх типов текста:
- Переписка из рабочего чата за определённый период
- Сообщение от Романа в личном чате с ботом
- Текст протокола встречи

Тебе известен проект, к которому относится этот текст: {project_name}
(один из: "Парк Горького", "Окко", "Аврора"; может быть null, если
определить нужно по содержанию — см. ниже)

ЧТО НУЖНО НАЙТИ
Найди ВСЕ задачи и договорённости в тексте — их может быть от 0 до
любого количества. Не ограничивайся одной задачей, даже если бот был
тегнут один раз — извлекай все договорённости из переданного контекста.

Задачей считается: явное поручение, обещание сделать что-либо,
договорённость о сроке выполнения чего-либо. Не считай задачей
обычное обсуждение без конкретного действия и исполнителя.

ДЛЯ КАЖДОЙ ЗАДАЧИ ОПРЕДЕЛИ
1. task_text — суть задачи кратко и ясно, в формате "что сделать"
2. assignee — имя исполнителя, как оно фигурирует в тексте
   (если неясно, кто исполнитель — пометь assignee_unclear: true)
3. category — выбери ОДНУ строго из этого списка, не придумывай новые:
   Техническое обеспечение, Сервис, Команда, Маркетинг, Бухгалтерия,
   Административные, Ноу-Хао, Управленческая отчётность
4. deadline — срок в формате YYYY-MM-DD, если упомянут явно или
   косвенно ("до пятницы", "на следующей неделе" — переведи в дату
   относительно сегодняшней даты: {current_date}). Если срок не
   упомянут — null.
5. project — если {project_name} известен заранее, используй его.
   Если null (личное сообщение/протокол без явной привязки к чату) —
   определи проект по исполнителю, если он уже встречается в одном из
   трёх проектов. Если определить невозможно — поставь project: null
   и project_unclear: true.
6. source_excerpt — точная цитата или фраза из текста, на основании
   которой ты сделал этот вывод (для проверки Романом)

ЕСЛИ НЕ УВЕРЕН
Если задача упомянута расплывчато (нет явного исполнителя или
непонятно, договорённость это или просто мысль вслух) — всё равно
включи её в список, но добавь поле confidence: "low" и кратко поясни
сомнение в source_excerpt.

ФОРМАТ ОТВЕТА
Ответь ТОЛЬКО валидным JSON, без преамбулы, без markdown-разметки.
Формат:

{
  "tasks": [
    {
      "task_text": "...",
      "assignee": "...",
      "assignee_unclear": false,
      "category": "...",
      "deadline": "2026-07-03",
      "project": "...",
      "project_unclear": false,
      "confidence": "high",
      "source_excerpt": "..."
    }
  ]
}

Если задач не найдено — верни {"tasks": []}
```

### 8.2. Промпт 2 — разбор ответа сотрудника на вопрос о статусе

```
Ты — модуль анализа ответов сотрудников для бота-менеджера проектов
Романа. Бот недавно спросил сотрудника о статусе конкретной задачи,
и сотрудник ответил. Твоя задача — разобрать этот ответ.

КОНТЕКСТ ЗАДАЧИ
Задача: {task_text}
Текущий срок: {deadline_current}
Текущий статус: {status}

ВОПРОС БОТА СОТРУДНИКУ
{bot_question}

ОТВЕТ СОТРУДНИКА
{employee_reply}

ЧТО НУЖНО ОПРЕДЕЛИТЬ

1. status_clear — true/false: можно ли из ответа однозначно понять
   текущий статус задачи. Если ответ расплывчатый, уклончивый или
   не содержит ясного указания на статус ("разбираюсь", "работаю
   над этим", без уточнения готовности/сроков) — поставь false.

2. new_status — один из: "в работе", "выполнена", "просрочена".
   Заполняется ТОЛЬКО если status_clear=true. Если status_clear=false
   — оставь null, статус не меняется автоматически.

3. clarifying_question — если status_clear=false, сформулируй прямой
   уточняющий вопрос для сотрудника (например: "Уточни, пожалуйста —
   задача уже выполнена, или ещё в процессе и нужен новый срок?").
   Если status_clear=true — null.

4. deadline_changed — true/false: упомянул ли сотрудник перенос срока

5. new_deadline — если deadline_changed=true, новая дата в формате
   YYYY-MM-DD (переведи относительные указания типа "на следующей
   неделе" относительно сегодняшней даты: {current_date}).
   Если перенос упомянут, но без конкретной даты — null, и в этом
   случае также верни status_clear=false с уточняющим вопросом про
   точный срок.

6. reason — если был перенос или есть сложности, кратко суть причины
   своими словами (1 фраза)

7. needs_help — true/false: просит ли сотрудник помощи Романа явно
   или косвенно

8. comment_summary — краткое резюме ответа сотрудника (1-2 фразы)
   для истории комментариев по задаче (заполняется всегда, даже
   если статус неясен — сам факт ответа стоит зафиксировать)

9. signal_type — определи, нужно ли мгновенно уведомить Романа.
   Один из: "завершение", "перенос_срока", "запрос_помощи", "нет"
   (если по ответу одновременно есть несколько признаков — приоритет:
   запрос_помощи > перенос_срока > завершение. Если status_clear=false
   и needs_help не true — signal_type обычно "нет")

ФОРМАТ ОТВЕТА
Ответь ТОЛЬКО валидным JSON, без преамбулы и markdown:

{
  "status_clear": true,
  "new_status": "...",
  "clarifying_question": null,
  "deadline_changed": false,
  "new_deadline": null,
  "reason": "...",
  "needs_help": false,
  "comment_summary": "...",
  "signal_type": "нет"
}
```

### 8.3. Промпт 3 — еженедельная аналитика (пятница, с разбивкой по проектам)

```
Ты — аналитический модуль еженедельной отчётности для бота-менеджера
проектов Романа. Тебе передана статистика за неделю по трём проектам:
Парк Горького, Окко, Аврора. Твоя задача — написать короткие,
содержательные наблюдения по каждому проекту отдельно, а затем дать
сводку по сотрудникам, занятым в нескольких проектах одновременно.
БЕЗ итоговых оценок или баллов эффективности — только факты и
наблюдения по фактам.

ДАННЫЕ ПО ПРОЕКТАМ
{projects_stats_json}

Структура входных данных — массив из трёх объектов, каждый содержит:
- project_name
- employee_stats: для каждого сотрудника (с assignee_telegram_id) —
  задач в работе, закрыто за неделю, просрочено, переносов за
  неделю, причины переносов, запросов помощи
- task_stats: задачи с 2+ переносами, задачи без обновления статуса
  дольше {stale_days} дней, задачи с близким сроком без прогресса
```

## 9. Технические требования и нюансы

1. **Telegram Bot API**: нельзя писать пользователю в личку без
   предварительной инициации диалога с его стороны (см. раздел 4).
   Нужен разовый онбординг-шаг для каждого сотрудника.
2. **Google Sheets API**: для программной записи нужен Service Account
   (создаётся в Google Cloud Console) с правами редактора на все три
   таблицы. Это отдельная настройка вне кода — должна быть выполнена
   до первого запуска бота.
3. **Буферизация сообщений в группах**: бот должен подписаться на все
   сообщения группового чата (получать их через polling/webhook) и
   хранить скользящее окно 2-3 часа в памяти/локальном хранилище —
   Telegram API не отдаёт историю до момента, когда бот начал слушать.
4. **Стек**: Python + Railway (хостинг) + Anthropic API (claude-sonnet-4-6)
   + Google Sheets API + python-telegram-bot + APScheduler — по аналогии
   со стеком уже существующих ботов Фёдор/Иван.
5. **Категории и проекты — строго фиксированные списки**, не давать
   Claude придумывать новые значения за пределами раздела 1.
